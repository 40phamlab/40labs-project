# ADR 0002 — Orbit Worker TLS Pinning on Local Area Network (LAN)

Status: **Accepted** — Date: 2026-10-02.

## Context
Orbit Worker communicates exclusively with the embedded Axum LAN hub in `40LabsCore` over the local pharmacy Wi-Fi (LAN). Because health and business data traverse shared local networks, plain HTTP is unacceptable, and standard public Certificate Authorities (CAs) cannot issue valid certificates for local IP addresses (`192.168.x.x`, `10.x.x.x`, `127.0.0.1`, or `.local` domains). 

Therefore, the desktop hub uses a persisted self-signed TLS certificate generated on first startup. To prevent Man-in-the-Middle (MITM) attacks on the local network, Orbit Worker must implement strict **TLS certificate / public key pinning**, verifying the hub's certificate against the SHA-256 fingerprint embedded in the pairing QR code.

## Tested Approaches & Evaluation

We evaluated three architectural approaches for React Native / Expo SDK 57:

1. **Maintained React Native Pinning Libraries (`react-native-ssl-public-key-pinning`, `react-native-cert-pinned-http`)**:
   - *Pros:* Pre-built native modules for iOS (`NSURLSession` delegate) and Android (`OkHttp` certificate pinner).
   - *Cons:* Compatibility issues with React Native 0.76+ New Architecture and Expo prebuild plugins; often abandon maintenance or lag behind Expo SDK upgrades.
2. **Native Configuration via Expo Config Plugins (Android Network Security Config + iOS TrustKit)**:
   - *Pros:* Leverages OS-native networking stacks directly without heavy bridging libraries; fully compatible with Expo prebuild and CNG (Config Native Generation).
   - *Cons:* Requires custom native configuration XML / plist generation; streaming and dynamic fingerprint updates require careful handling.
3. **Custom Expo Native Module (`expo-orbit-pinning`)**:
   - *Pros:* Full control over pinning verification, custom error handling (distinguishing revoked/untrusted vs pinned mismatch), and exact matching with our Axum hub.
   - *Cons:* Higher initial engineering overhead.

## Exact Fingerprint Definition
- **Algorithm:** SHA-256 hash.
- **Target:** DER-encoded Subject Public Key Info (SPKI) or full X.509 certificate DER.
- **Encoding:** Hex-encoded string (64 characters) or Base64, passed as `fp=<sha256-hex>` in the pairing QR code (`orbit://pair?endpoint=...&sessionId=...&token=...&fp=...`).

## Certificate Requirements
- Generated by Tauri desktop hub (`40LabsCore`) using `rcgen` or native crypto primitives on first launch.
- Persisted securely in the desktop app data directory.
- Validity: Long-lived (e.g. 10 years) to prevent expiration disruptions on isolated LANs.
- Subject Alternative Names (SANs): Includes local IP addresses and device hostname.

## Native Configuration & Recommended Implementation
1. **Android**: Use an Expo config plugin to generate `app/src/main/res/xml/network_security_config.xml` declaring domain-specific certificate pins (SHA-256 hash of SPKI).
2. **iOS**: Configure TrustKit via Expo config plugin in `Info.plist` or implement a custom `NSURLSession` delegate in a lightweight Expo native module that verifies the certificate fingerprint against the securely stored credential (`expo-secure-store`).
3. **Transport Layer**: All API calls from `@40labs/api-client` are routed through the pinned fetch implementation.

## Risks & Mitigations
- **DHCP IP Changes**: Mitigated by embedding the hub endpoint URL in pairing metadata, allowing mDNS or reconnection discovery if IP changes while retaining the same pinned certificate fingerprint.
- **Certificate Renewal**: If the hub revokes/regenerates its certificate, paired devices must re-pair via QR code.

## Impact on Step 0C / O2
This pinning spike validates that Orbit Worker can securely and reliably communicate with the desktop LAN hub with cryptographic verification, preventing local network eavesdropping and MITM tampering on shared pharmacy Wi-Fi networks.
